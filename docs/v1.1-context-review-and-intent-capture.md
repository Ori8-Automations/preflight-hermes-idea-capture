# Preflight v1.1 — Context Review and Intent Capture

Status: implemented in the backend (`v1.1.0`); dashboard review UI still outstanding

Target: `v1.1.0`

Implementation notes (where the shipped backend is more specific than this
document):

- The input revision covers operator-authored **timeline updates** as well as the
  form fields, so a note carrying the missing intent invalidates an in-flight
  event.
- Events carry a **generation** counter. `Review again` bumps it, which makes a
  re-review a distinct event even for byte-identical content, and the previous
  completed review is retained until a replacement lands.
- Correlation tokens carry **issuance and expiry** timestamps, and resolution
  handles zero/one/many matches explicitly — ambiguous tokens are refused.
- The outbox adds a `processing/` lease directory; events are claimed by atomic
  rename so concurrent drains cannot double-process one event.
- Draining and follow-up delivery are **explicit operations**
  (`POST /review-events/drain`, `POST /review-events/send-followups`); there is
  no background scheduler.

Scope: event-driven review of newly captured ideas without automatic promotion or execution

## Problem

Preflight is deliberately optimized for low-friction capture. An operator may save a rough thought or paste only a link, then return later with no memory of why it mattered.

A source reviewer can usually determine **what a link contains**. It cannot safely infer **why the operator saved it**. Preflight v1.1 should preserve both:

1. source context — what the item is;
2. operator intent — why it was interesting or potentially useful.

The feature should enrich the capture record without turning every thought into active work.

## Product decision

Preflight v1.1 will add an optional, event-driven review flow built around a durable local outbox and a bounded Hermes webhook reviewer.

The first implementation should not require n8n. n8n may become an optional adapter later if the system needs multi-service enrichment, queue visualization, or additional sinks.

## Goals

- Preserve friction-free capture: saving an idea must not wait for model inference or source retrieval.
- Review new ideas asynchronously after a configurable grace period.
- Summarize public source material and suggest classification.
- Ask the operator one concise follow-up when personal intent is missing.
- Correlate the answer to the correct idea even after other conversation has occurred.
- Keep source facts, agent interpretation, and operator intent visibly separate.
- Fail closed around promotion and execution: review may enrich an idea but may not create work.
- Remain useful when Hermes, the model provider, or the linked source is unavailable.

## Non-goals

v1.1 does not:

- create or dispatch Kanban cards;
- create projects, tickets, scheduled jobs, or approval records;
- archive, delete, or promote ideas automatically;
- bypass Hermes command approval;
- require authenticated browsing or reuse browser cookies;
- require n8n;
- treat agent-suggested classification as operator intent;
- make review success a prerequisite for idea capture.

## User experience

### Context-rich capture

When the idea already includes enough operator context, the reviewer works silently and appends a structured review. The UI shows a review-state badge.

### Link-only or context-poor capture

After the grace period, the reviewer:

1. identifies and summarizes the public source when safely retrievable;
2. records a provisional classification;
3. marks the item `needs_context` when the operator's reason cannot be established;
4. sends one concise follow-up message containing a short correlation token.

Example:

> **Preflight follow-up · PF-A346**
>
> You saved **Hermes Flightplan**, a bounded authority system for agent work.
>
> What caught your attention: using it directly, borrowing a design pattern, researching it later, or keeping it as a reference?

The operator may reply naturally or with shorthand such as:

- `reference only`
- `research later`
- `possible internal tool`
- `possible business idea`
- `not sure anymore`

The answer is appended as operator-provided intent. It does not silently replace the original notes.

### Notification budget

- Wait a configurable grace period before reviewing; proposed default: 10 minutes.
- Send no message when sufficient intent is already present.
- Send at most one unanswered follow-up per idea revision.
- Group multiple context-poor captures into a compact digest when they arrive close together.
- Reserve immediate separate alerts for an independently defined urgent-risk policy; v1.1 review itself does not promote risk work.
- Provide `Review again` and `Dismiss follow-up` controls.

## Review output

A completed review should contain:

- source title and plain-language source summary;
- source kind: article, repository, product, video, discussion, research, other;
- suggested lane, category, and subcategory;
- related or possible duplicate idea IDs;
- potential value;
- rough effort and risk notes;
- recommended disposition:
  - `keep_reference`
  - `needs_context`
  - `research_later`
  - `shape_into_plan`
  - `possible_project`
  - `archive_candidate`
- one specific follow-up question when required;
- reviewer version, timestamps, source-retrieval status, and input revision.

Recommendations are advisory. They do not mutate status, category, priority, archival state, or Kanban state without a separate operator action.

## Record model

Keep existing idea fields backward-compatible. Add an optional review envelope rather than blending machine output into `notes_markdown`.

Illustrative shape:

```json
{
  "review": {
    "state": "waiting|reviewing|reviewed|needs_context|followup_sent|answered|failed|dismissed",
    "input_revision": "sha256:...",
    "reviewer_version": "preflight-context-review/1",
    "source": {
      "retrieval_status": "not_needed|ok|blocked|failed",
      "title": "...",
      "kind": "repository",
      "summary": "..."
    },
    "classification": {
      "suggested_lane": "internal-operations",
      "suggested_category": "...",
      "suggested_subcategory": "...",
      "related_idea_ids": [],
      "potential_value": "...",
      "effort": "low|medium|high|unknown",
      "risk": "low|medium|high|unknown",
      "recommended_disposition": "research_later"
    },
    "intent": {
      "status": "present|missing|requested|answered|dismissed",
      "question": "...",
      "correlation_token": "PF-A346",
      "answer": "...",
      "answered_at": "...",
      "answered_via": "preflight|telegram|api"
    },
    "created_at": "...",
    "updated_at": "...",
    "error_code": null
  }
}
```

Do not store source-page bodies, model chain-of-thought, secrets, cookies, broad request headers, or raw tool logs in the idea file.

## Event and outbox contract

Idea persistence remains authoritative and completes first.

```text
POST /ideas
  -> atomically save idea
  -> atomically enqueue local event
  -> return saved idea immediately
  -> asynchronous sender delivers event
```

Suggested layout:

```text
<DATA_ROOT>/
  events/
    pending/
    delivered/
    failed/
```

Minimal event payload:

```json
{
  "schema_version": 1,
  "event_id": "evt_...",
  "event_type": "idea.created",
  "idea_id": "idea_...",
  "idea_revision": "sha256:...",
  "created_at": "..."
}
```

The event must not include the full idea body or fetched source content. The reviewer retrieves the canonical record by validated idea ID.

### Delivery properties

- Deterministic idempotency key: event type + idea ID + input revision.
- Bounded retry with durable attempt metadata.
- Capture remains successful if enqueue delivery or review fails.
- A stale event may not overwrite a newer review revision.
- `Review again` creates a new event bound to the current input revision.
- Delivered/failed retention must be bounded and configurable.

## Hermes reviewer boundary

The proposed reviewer may:

- read the one event-bound idea;
- fetch public HTTP/HTTPS source material through a restricted retrieval path;
- compare against bounded local Preflight metadata for duplicate suggestions;
- write one review envelope and append review/intent timeline updates;
- emit one correlated clarification notification.

It may not:

- read arbitrary filesystem paths;
- use authenticated browser sessions, stored cookies, or broad credentials;
- execute terminal commands as a substitute for a missing narrow interface;
- modify unrelated ideas;
- change operator-authored title, summary, notes, category, status, priority, tags, archive state, or promotion state;
- create projects, cards, tickets, jobs, messages other than the scoped clarification, or external writeback.

Webhook transport should use HMAC authentication. Payload fields and fetched pages remain untrusted after transport authentication.

## API additions

Exact routes may change during implementation, but the contract needs narrow operations equivalent to:

- `POST /ideas/{id}/review-events` — enqueue/re-enqueue review for the current revision;
- `GET /ideas/{id}/review` — return the review envelope;
- `POST /ideas/{id}/intent-answer` — append an operator answer bound to a valid pending correlation token;
- `POST /ideas/{id}/review-dismiss` — dismiss the current follow-up without changing the idea disposition;
- `GET /review-events` — local/operator diagnostics with no secret material.

Existing `POST /ideas/{id}/updates` may continue to carry human-readable timeline summaries, but the structured review envelope is authoritative for review state.

## Correlation and replies

- Tokens must be unique enough for the retained idea set, human-readable, and non-authoritative on their own.
- A write requires both the token and server-side resolution to the pending idea/revision.
- Expired, already-used, mismatched, or ambiguous tokens fail closed.
- Replaying the same answer is idempotent.
- A reply to an older revision must not overwrite a newer intent answer.

## Source retrieval safeguards

- Accept only absolute `http://` and `https://` sources.
- Resolve and reject loopback, link-local, private, reserved, and metadata-service destinations before every request and redirect.
- Apply response-size, redirect-count, and time limits.
- Do not download arbitrary binary attachments in v1.1.
- Do not execute page instructions or treat page content as agent authority.
- Do not use authenticated sessions or operator cookies.
- Store only bounded summaries and retrieval metadata.
- Treat inability to retrieve as an ordinary `blocked` or `failed` source state, not a capture failure.

## UI additions

- Review-state badge on list and detail views.
- Separate sections for:
  - Source summary
  - Operator intent
  - Agent review
  - Suggested disposition
- `Review again`, `Answer`, and `Dismiss follow-up` controls.
- Clear labels distinguishing operator-authored and agent-generated content.
- Mobile layout must keep the original idea visible without burying it below review detail.

## Configuration

Proposed optional settings:

```json
{
  "context_review": {
    "enabled": false,
    "grace_period_seconds": 600,
    "max_delivery_attempts": 5,
    "followup_delivery": "none",
    "digest_window_seconds": 900,
    "event_retention_days": 30,
    "intent_token_ttl_seconds": 1209600,
    "fetch_max_bytes": 1048576,
    "fetch_timeout_seconds": 10,
    "fetch_max_redirects": 5
  }
}
```

The last four settings were added during implementation: an explicit token
lifetime, and the bounds enforced by the public-source fetch path.

The feature defaults off until a reviewer route is explicitly configured. Preflight remains fully functional without Hermes webhook review.

## Acceptance criteria

### Capture and durability

- Idea creation returns successfully when the reviewer is unavailable.
- The saved idea and pending event survive process restart.
- Duplicate delivery does not create duplicate reviews or messages.
- A stale event cannot overwrite a review for newer idea bytes.

### Review correctness

- Context-rich ideas can complete without a follow-up.
- Link-only ideas produce source context plus `needs_context` when intent is unknown.
- Source facts, suggestions, and operator intent remain separate.
- Retrieval failure produces a bounded review state without losing the idea.

### Intent capture

- A follow-up contains a short correlation token and one specific question.
- A valid reply updates only the bound idea/revision.
- Replayed, expired, wrong, or ambiguous tokens fail closed.
- `not sure anymore` is accepted as a valid operator answer.
- Notification batching and one-unanswered-follow-up limits are tested.

### Authority and security

- Review cannot mutate operator-authored fields or promotion/archive/Kanban state.
- Review cannot read or write outside the approved data root and narrow interfaces.
- Public-source retrieval blocks SSRF targets across redirects.
- Raw source bodies, secrets, cookies, and tool logs are absent from persisted review data.
- Webhook authentication and idempotency are tested independently.

### Compatibility

- Existing v1.0 idea files load unchanged.
- Export/import round trips preserve optional review state safely.
- Disabling context review restores existing behavior without data migration.
- Existing API and smoke tests remain green; new tests cover outbox, review state, correlation, notification budgeting, and source safeguards.

## Suggested implementation sequence

1. Define backward-compatible review/event schemas and tests.
2. Add durable outbox write after successful idea persistence.
3. Add idempotent sender/retry state without enabling external delivery.
4. Add structured review API and UI sections.
5. Add a fixture-only reviewer adapter and adversarial tests.
6. Add optional HMAC Hermes webhook delivery.
7. Add intent-token answer flow and notification budget.
8. Run independent security/authority review before enabling the route in a live installation.
